# Step 5. Add tracing utilities

Automatic FastAPI instrumentation captures incoming HTTP requests, but it does not automatically give us the full 
business-level visibility we need inside every LangGraph node.

We'll create a reusable tracing helper.

What this provides

Every time we use trace_operation(), we get a span with:

    - Operation name.
    - Duration.
    - Optional attributes.
    - Exception information.
    - Success or failure status.

We deliberately re-raise exceptions. Tracing must not swallow errors or change your existing recovery 
behavior.

# Step 8. Record execution outcomes and evidence counts

Provider spans alone do not tell us whether the complete underwriting execution succeeded.

We should attach final outcome information to the workflow's root execution span.

There are two ways to do this:

- Create an explicit execution span around the graph.ainvoke() call in the API route.
- Rely on the automatically instrumented HTTP request as the parent span.

I recommend the first approach because the underwriting execution is a business operation, whereas the HTTP request is 
a transport-level operation.

Adapt this to your current route. Preserve existing request validation, checkpoint configuration, and response handling.

# Why this matters

When investigating an execution, we can inspect:

- Its total duration.
- Its final execution status.
- Its evidence count.
- Its recorded errors.
- The nested LangGraph node spans.
- The nested provider spans.

Do not attach full property addresses, account names, raw prompts, or scraped content to spans by default. Those values 
are unnecessary for basic diagnostics and can create privacy and telemetry-volume problems.

Also note that an exception raised from graph.ainvoke() will mark the execution span as failed. 
If your workflow returns execution_status="failed" without raising an exception, the code above records that 
outcome as an attribute, but does not automatically mark the span as an error. We should explicitly set the span 
status based on the final execution status.



# 11. Important refinements before calling this branch complete

The preceding steps establish the instrumentation foundation. Before considering the branch production-ready, we should address several details.

# A. Explicit service resource metadata

The configured OTEL_SERVICE_NAME should be attached to the OpenTelemetry resource as service.name.

We should verify that Azure Monitor receives this resource attribute. Merely writing the service name into application logs is insufficient.

# B. Per-attempt retry spans

The initial provider wrappers measure the complete retry sequence. For detailed recovery diagnostics, instrument each individual attempt inside retry_async().

This should be done without changing its retry behavior.

# C. Accurate token usage

Record actual provider-reported usage. Do not assume that every response contains the same usage fields or that every failed request consumes zero tokens.

# D. Async-safe instrumentation

Your graph and provider services use asynchronous functions. The instrumentation must preserve their async behavior and avoid blocking the event loop.

# E. Telemetry privacy and volume

Avoid collecting raw prompts, full scraped pages, secrets, and sensitive property information. Use sampling and retention settings appropriate to the expected workload.

# F. Trace correlation

Verify that FastAPI request spans, execution spans, graph-node spans, and provider spans appear in a coherent parent-child hierarchy.

A collection of unrelated spans is not sufficient for distributed tracing.
