4.2 app/observability/telemetry.py

    This module initializes the telemetry SDK and instruments FastAPI.

    Why this design?
        Initialization happens once per process.
        Missing configuration does not crash local development.
        Azure Monitor initialization failures do not prevent application startup.
        FastAPI receives automatic instrumentation.
        We keep instrumentation setup separate from business logic.

Important: The service name should be configured as the OpenTelemetry resource's service.name. 
In the next step, we'll refine resource configuration so that the name is explicitly attached 
to exported telemetry rather than only included in application logs.

Also, configure_azure_monitor() configures Azure Monitor's telemetry pipeline. 
Avoid initializing competing global providers or independently instrumenting the same FastAPI 
application multiple times.

# Step 5. Add tracing utilities

Automatic FastAPI instrumentation captures incoming HTTP requests, but it does not automatically give us the full 
business-level visibility we need inside every LangGraph node.

We'll create a reusable tracing helper.

What this provides

Every time we use trace_operation(), we get a span with:

    - Operation name.
    - Duration.
    - Optional attributes.
    - Exception information.
    - Success or failure status.

We deliberately re-raise exceptions. Tracing must not swallow errors or change your existing recovery 
behavior.

# What we gain #

Azure Monitor can now show a trace with distinct operations for each LangGraph node, allowing us 
to identify where time is spent.

For a node failure, the span will capture the exception and mark the operation as failed. 
Existing recovery and error handling remain responsible for deciding whether the workflow continues.
