# Final recommendation

Start with OpenTelemetry, not Prometheus alone. Build tracing and application-level metrics first; add Prometheus 
and Grafana for operational monitoring after the instrumentation is working.

This gives your agent visibility into both **"what happened during an execution"** and **"how the system performs across many 
executions."**

# 1. Purpose and big picture

The purpose of this branch is to make the Underwriting Intelligence Agent observable, traceable, and easier to debug in 
production.

Currently, your agent executes a workflow involving LangGraph, Tavily, Firecrawl, and Azure OpenAI. If an execution is 
slow, a provider fails, or the workflow produces an incomplete report, we need visibility into what happened at each stage.

We will use OpenTelemetry for instrumentation and tracing, and Azure Monitor Application Insights for collecting and 
analyzing telemetry.

OpenTelemetry captures the operational details of your application. Azure Monitor gives you a centralized place to 
inspect traces, requests, dependencies, exceptions, and logs.

# 2. What metrics and telemetry will we measure?

We should distinguish between metrics, which measure aggregate performance, and traces, which explain individual executions.

# A. Execution and workflow telemetry

Measurement	                                Purpose

Execution ID	                Correlate operations belonging to one execution
Total execution duration	    Measure end-to-end workflow latency
Execution outcome	            Track completed, completed with errors, and failed executions
Graph node duration	            Identify slow nodes
Graph node errors	            Identify where failures occur
Evidence count	                Understand how much usable evidence was collected
Report generation status	    Determine whether synthesis completed successfully

# B. Provider telemetry
Provider	                               Measurements

Tavily	                        Search duration, success/failure, retry count, results returned
Firecrawl	                    Scrape duration, extraction status, retry count, errors
Azure OpenAI	                Request duration, success/failure, token usage, retry count

# C. Recovery and error telemetry

- Retry attempts and reasons.
- Final provider outcome.
- Exception type and relevant diagnostic context.
- Workflow failures and partial successes.
- Time spent on failed attempts.

# D. Application telemetry

FastAPI instrumentation will help capture incoming requests, HTTP status codes, and request durations.

The OpenTelemetry instrumentation will also let us correlate application activity with provider operations.

# Important distinction

In this branch, we will focus on:

- Traces for individual executions and provider calls.
- Application and dependency metrics.
- Structured diagnostic logging.
- Token usage and retry details where explicit instrumentation is required.
