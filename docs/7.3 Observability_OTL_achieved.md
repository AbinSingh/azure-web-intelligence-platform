# 5. Is duration automatic by OTEL?


Yes, the duration is being captured automatically by OpenTelemetry instrumentation, even though you haven't explicitly defined duration measurements in your application code.

In your current implementation, duration comes from two sources.

# 5.1. Where is duration captured?

# Component	        How duration is captured	            Explicit timing code required?

POST /underwrite	FastAPI request instrumentation	                    No
fastapi.endpoint	Framework instrumentation and spans	            Usually no
underwriting.execute	Your custom OpenTelemetry span	                No
langgraph.node.*	Your custom node-level spans	                    No
tavily.search	Your custom provider span	                            No
firecrawl.scrape	Your custom provider span	                        No
azure_openai.generate	Your custom provider span	                    No
fastapi.serialization	Framework instrumentation	                    No

OpenTelemetry records the start and end times of each span. The elapsed time is calculated automatically 
when the span ends. Azure Application Insights receives that timing data and displays it as duration.

For example, your custom span:

    with trace_operation("underwriting.execute") as span:
        final_state = await graph.ainvoke(initial_state, config=config)

doesn't need a stopwatch. The span's duration covers the time spent inside the with block.

# 5.2. What about node-level duration?

If trace_node wraps the function in an OpenTelemetry span, OpenTelemetry automatically 
measures the time taken by that node.

# 6. What should we implement ourselves?

OpenTelemetry automatically measures span durations, but it doesn't automatically understand every 
business metric your underwriting application needs.

For your next improvements, I'd distinguish these categories:

Metric or information	        Automatically available?

HTTP request duration	    Yes, with FastAPI instrumentation
Custom node duration	    Yes, if the node is wrapped in a span
Provider-call duration	    Yes, if the provider call is wrapped in a span
Execution ID	            No, you add it as a custom attribute
Evidence count	            No, you add it as a custom attribute
Underwriting execution outcome	Not reliably; set it explicitly
Retry-attempt count	        No, instrument retries explicitly
Azure OpenAI token usage	No, capture it from the API response and record it
Business-level success criteria	No, define them in your application

My recommendation

Your current telemetry confirms that automatic duration tracking and custom span instrumentation are working.

Before moving to Prometheus and Grafana, I would finish three things:

Retry tracing: record each provider retry attempt separately.
Token usage: capture input and output tokens from Azure OpenAI responses.
Execution outcome: explicitly record whether the underwriting workflow completed successfully, completed with errors, or failed.

# 8. OpenTelemetry hierarchy

Yes, you're close. In OpenTelemetry (OTel), the hierarchy is slightly different: a trace contains spans, spans can have 
parent–child relationships, and each span contains attributes, events, and timing information.

TRACE (one complete underwriting execution)
│
├── Span: POST /underwrite
│   │
│   ├── Span: underwriting.execute
│   │   │
│   │   ├── Span: langgraph.node.build_search_queries
│   │   │
│   │   ├── Span: langgraph.node.discover_web_sources
│   │   │   └── Span: tavily.search
│   │   │
│   │   ├── Span: langgraph.node.extract_evidence
│   │   │   └── Span: firecrawl.scrape
│   │   │
│   │   └── Span: langgraph.node.synthesize_underwriting_report
│   │       └── Span: azure_openai.generate
│   │
│   └── Span: fastapi.serialization
│
└── Each span contains:
    ├── Attributes
    ├── Events
    ├── Start time and duration
    ├── Status (OK / ERROR / unset)
    └── Span ID and trace context

# What level each means

| Level               | Purpose                                                   | Example                        |
| ------------------- | --------------------------------------------------------- | ------------------------------ |
| **Trace**           | Represents the complete end-to-end operation.             | One underwriting API execution |
| **Span**            | Represents a single operation within the trace.           | `tavily.search`                |
| **Span attributes** | Store searchable metadata about that operation.           | `provider.name=tavily`         |
| **Span events**     | Record notable occurrences during a span.                 | Retry attempted                |
| **Span status**     | Indicates whether the operation succeeded or failed.      | `ERROR`                        |
| **Span timing**     | Captures when the operation started and how long it took. | `duration=3.2s`                |


# The key takeaway

Your mental model should be:

    Trace → Parent/child spans → Span data (attributes, events, status, and timing).

For your underwriting agent, this lets you follow an execution from the incoming API request through LangGraph nodes 
and external providers, while inspecting each operation's duration, outcome, and metadata.
