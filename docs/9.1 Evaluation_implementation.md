# Stage 1 — Search evaluation

Goal: Determine whether Tavily discovers the expected relevant URLs.

| Metric    | Purpose                                                         |
| --------- | --------------------------------------------------------------- |
| Precision | Of the URLs retrieved, what proportion are in the ground truth? |
| Recall    | Of the ground-truth URLs, what proportion were retrieved?       |
| F1 score  | Balances precision and recall.                                  |

We'll normalize URLs before comparing them, ignoring fragments, trailing slashes, and common tracking parameters.

# Stage 2 — Scrape evaluation

Goal: Verify whether Firecrawl preserves the expected facts from each source.

We'll use an LLM-as-a-judge to compare the expected facts against the extracted page content.

| Metric            | Purpose                                                                           |
| ----------------- | --------------------------------------------------------------------------------- |
| Fact support rate | Percentage of expected facts supported by the extracted content.                  |
| Fact coverage     | Percentage of expected facts successfully recoverable from the extracted content. |


For the initial version, these can be combined into one metric: Expected Fact Pass Rate.

The judge will classify each fact as supported or unsupported and provide a brief reason. 
It must evaluate the supplied content, not its own external knowledge.

# Stage 3 — Final output evaluation

Goal: Check whether the agent produces the expected underwriting answers.

| Answer type         | Evaluation method                         | Metric                |
| ------------------- | ----------------------------------------- | --------------------- |
| Yes/No              | Normalize and compare answers             | Accuracy              |
| Pick list           | Compare expected and predicted selections | Precision, Recall, F1 |
| Evidence references | Verify referenced IDs exist               | Valid reference rate  |

For free-text findings, we won't require exact wording. The scrape evaluator assesses fact preservation; final-output 
evaluation checks answer correctness against the ground truth.

# Why use an LLM here?

Suppose the expected fact is: The property is located in a designated flood zone.

The extracted content says: The property falls within the mapped special flood hazard area.

A simple string comparison may fail, even though the content supports the expected fact. The LLM judge can assess 
semantic equivalence.

Important: An LLM judge is not ground truth. For a production-quality evaluation, manually verify a small sample of its 
decisions and keep its model/configuration consistent between evaluation runs.

The code also treats invalid judge output as an evaluation error rather than silently counting it as a successful result.

# 7. How we will run the evaluations

The evaluation runner will load the dataset and actual execution results, call the three evaluators, and produce a 
summary JSON report.

The actual results should have this general shape:

    [
      {
        "case_id": "property_001",
        "search_returned_urls": [
          "https://example.com/property-001/flood"
        ],
        "scrape_results": [
          {
            "url": "https://example.com/property-001/flood",
            "extracted_content": "Saved extracted webpage content goes here."
          }
        ],
        "actual_answers": [
          {
            "question_id": "q1",
            "answer": "yes"
          }
        ]
      }
    ]
    
This is an example of the evaluation input format, not a claim that the example URL contains the expected facts.

For each case, the runner will:

    - Compare returned URLs against ground truth.
    - Send extracted content and expected facts to the LLM judge.
    - Compare final answers against expected answers.
    - Save scores, failed checks, and reasons to evals/results/evaluation_report.json.

We'll use saved results for repeatable regression tests and run a smaller live-provider evaluation separately when needed.

# 8. What constitutes success?

For the initial branch, we'll report the metrics rather than pretend that three samples establish production readiness.

| Component    | Reported metric                         |
| ------------ | --------------------------------------- |
| Search       | Precision, recall, F1                   |
| Scrape       | Expected fact pass rate                 |
| Final output | Accuracy, pick-list precision/recall/F1 |
| Overall      | Number of checks passed and failed      |

# Final implementation scope

We'll keep this branch to:

    - Three initial evaluation cases.
    - Deterministic search and answer evaluators.
    - An LLM-based scrape evaluator.
    - A JSON evaluation report.
    - Tests for URL normalization, missing results, incorrect answers, and malformed judge output.

No separate evaluation platform, no complex LLM-as-a-judge framework, and no changes to your production workflow until 
the evaluation logic is validated.

# create run_evaluation
The run_evaluation.py file orchestrates all three evaluation stages: search, scrape, and final output. 
It loads the ground-truth dataset and saved execution results, runs the evaluators, and writes a consolidated JSON report.

# One important detail: 
This initial version uses strict pass criteria: perfect search recall, perfect expected-fact pass 
rate, and perfect final-answer accuracy. Treat those as initial regression gates, not production-readiness thresholds. 
Also, URL normalization must be applied consistently when matching expected scrape URLs to actual scrape results; 
otherwise, URL variants can be incorrectly marked missing.
